# エージェント編成

オーナー（駒場さん）がプロダクトオーナーとして開発を回すための、役割分担の定義。

## 設計方針: 「役職」ではなく「関門」で分ける

肩書きを与えたエージェントは、専門知識ではなく役割演技を出力しがちです。
価値が出るのは**別の情報源を見る**か**別の検査をする**場合だけなので、
この4つはそれぞれ固有の検査を持っています。

| 役割 | 固有の持ち場 | いつ呼ぶか |
| :--- | :--- | :--- |
| `pm` | **次に何をやるか決めて指示を出す。** 「やらないこと」「成功の判定」の確定 | 「続けて」と言われたとき、実機の結果が返ったとき、機能追加の**前** |
| `architect` | 既存コードの手本を探し、選択肢とコストを出す | 複数ファイル・外部API・新依存に触る**前** |
| `qa` | **成果物そのもの**（APKの中身、リソースの解決先）を検査する | 実装後、オーナーに渡す**前** |
| `security` | 秘密情報の混入・権限の増加・依存の素性を機械的に検査する | コミット前、公開範囲を変えるとき |

デザイナー・広報・財務は常設しません。変更のたびに回すと費用対効果が合わないためで、
必要時（リリース時のPRFAQ、API課金の見積り）に都度依頼する方が向いています。

## オーナーの役割 — 指示出しはしない

オーナー（駒場さん）がやるのは次の3つだけ。

1. **方向性と優先順位を決める**（何を目指すか、何を先にやるか）
2. **可否を判断する**（提示された選択肢から選ぶ、進めるか止めるか）
3. **人にしかできない操作**（実機での確認、Cloud Console の設定）

**「次に何をやるか」を考えるのはオーナーの仕事ではない。** それは `pm` の仕事。
オーナーが「続けて」と言えば、`pm` が状態を読んで次の作業を決め、指示を出す。

3つ目は**能力の限界**であって、PMの仕事を渡していい理由ではない。
実機確認を頼むときも、**手順表を渡して解釈させない**。
「何をして、何を見て、それを伝えてほしい」までに留め、
**返ってきた結果を解釈して次の手を決めるのはこちら側**。

> この節は、初回の1周（2026-07-30、地図タップ不具合）で実際に失敗した点。
> 毎回オーナーに手順表と判定表を渡しており、事実上オーナーにPMをやらせていた。
> 指摘を受けて `pm` を「要望を待つ受け身の役」から「次を決めて指示を出す役」に
> 定義し直した。

## 制約

- **エージェント同士は直接会話しません。** 全員メインのセッションに報告します。
  「PMとアーキテクトの議論」は、メインが両者の出力を突き合わせる形になります
- **毎回ゼロから起動します。** 前の会話を引き継がないので、必要な文脈は
  呼び出し側が渡す必要があります。人数を増やすほど遅く・高くなります
- 全員 **コードを書きません**。書くのはメインのセッションです

## 一番効くのはエージェントではない

エージェントは毎回記憶を失いますが、書いて残した文書は残ります。
決定と教訓は [cloud42-labo/brain](https://github.com/cloud42-labo/brain) に置きます
（`decisions/` `notes/` `projects/`）。ここが機能しているかが先で、
エージェントはその上に載るものです。

増やす前に減らす方向で調整してください。
